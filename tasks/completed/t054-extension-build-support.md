## Goal

Make the extension system buildable, testable, and documented. After t053 defines
the API/ABI boundary, this task decides how extensions are built and enabled, and
gives future extension authors a clear path to follow.

## Context

ADR 0005 P3-2. With the extension API defined (t053), the question is: how does
an extension get built into the binary? Options are dynamic loading (dlopen) or
conditional static linking. The choice must be made and documented here, because
t055 (converting Redis to a real extension) depends on it.

**Static vs. dynamic loading decision:**

wrkx is a performance benchmarking tool. Key constraints:
- No startup latency from dlopen/symbol resolution during a benchmark run
- Simple deployment: single binary, no .so search-path issues
- Extensions must not introduce race conditions in the hot path
- Extensions are selected at build time, not at runtime

**Decision: static linking with a manifest-driven build.** Extensions are compiled
into the binary as static libraries. The extension manifest (a Makefile fragment)
declares which extensions are active. No dlopen, no RTLD_GLOBAL. This is recorded
as a project decision in this task file's "Accepted decisions" section and
referenced in `docs/extension-invariants.md`.

Dynamic loading is explicitly deferred — a future ADR may add it when there is a
concrete reason (e.g. third-party extension distribution). Gate C does not require
it.

## Deliverables

### 1. Extension directory structure

```
extensions/
    README.md               # "how to write an extension" (brief)
    toy/
        toy.c               # toy extension from t053, moved here
        Makefile.ext        # extension build fragment
```

Each extension lives in `extensions/<name>/` and provides a `Makefile.ext`
fragment that declares:
- `EXT_SRCS` — source files
- `EXT_CFLAGS` — any extra compiler flags
- `EXT_HDRS` — public headers the extension exposes (if any)

### 2. Top-level Makefile: extension build support

New variable: `EXTENSIONS` (space-separated list, default: none).

```makefile
# Enable extensions at build time:
#   make EXTENSIONS="toy redis"
EXTENSIONS ?=
```

For each extension in `EXTENSIONS`:
- Include `extensions/$(ext)/Makefile.ext`
- Add `$(EXT_SRCS)` to the main build
- Add `-Iextensions/$(ext)` to `CFLAGS`
- Call a generated `_register_extensions()` function that invokes each
  extension's `wrkx_extension_init(api)` at startup

The `_register_extensions()` function is generated by `make` from the list of
active extensions — no hand-editing of `main.c` when adding an extension.

### 3. Extension registration in `main.c`

Replace the hard-coded `#include "proto/redis.h"` / `redis_configure()` /
`lua_register_redis_helpers()` pattern with a call to `register_extensions(api)`
at startup. (The actual Redis → extension move is t055; this task sets up the
mechanism and tests it with the toy extension only.)

The generated `register_extensions.c` (or a macro approach) calls each active
extension's init function in declaration order.

### 4. `make check-extension-headers` target (finalize from t053)

Concrete implementation: for each `*.c` file in each active extension directory,
run `$(CC) -M` and grep for `src/` paths. Fail the build if any appear.

```makefile
check-extension-headers:
	@for f in $(EXT_SRCS); do \
	    deps=$$($(CC) $(CFLAGS) -M $$f); \
	    bad=$$(echo "$$deps" | grep -o 'src/[^ ]*' | grep -v '^$$'); \
	    if [ -n "$$bad" ]; then \
	        echo "FAIL: $$f depends on private header: $$bad"; exit 1; \
	    fi; \
	done
	@echo "check-extension-headers: PASS"
```

### 5. CI matrix

Add a CI step (`.github/workflows/ci.yml`) that builds and tests with the toy
extension enabled:

```yaml
- name: Build with toy extension
  run: make EXTENSIONS=toy check-extension-headers test-unit
```

This runs alongside the existing no-extension build — both must be green.

### 6. Developer documentation

`extensions/README.md` — "How to write a wrkx extension" (one page):

1. Create `extensions/<name>/` directory
2. Include only `include/wrkx_extension.h`
3. Implement `void wrkx_extension_init(const wrkx_extension_api *api)`
4. Check `api->version == WRKX_EXTENSION_API_VERSION` before using any field
5. Call `api->register_protocol(...)` and/or `api->register_helpers(...)` as
   needed
6. Write `Makefile.ext` declaring `EXT_SRCS`
7. Build with `make EXTENSIONS=<name>`, test with `make test EXTENSIONS=<name>`

Also document the "do not touch" list (link to `docs/extension-invariants.md`).

## Guards / Acceptance

1. `make EXTENSIONS=toy` builds cleanly — toy extension compiled and linked.
2. `make EXTENSIONS=toy check-extension-headers` passes.
3. `make EXTENSIONS=toy test-unit` — all existing unit tests still pass;
   toy extension's init function is called at startup (verified by a log line
   or a unit test hook).
4. `make EXTENSIONS=` (empty, the default) builds identically to the pre-t053
   binary — no regression for the no-extension build path.
5. CI matrix green on both Linux and macOS.
6. `extensions/README.md` exists and covers the 7-step walkthrough.

## What this does NOT do

- Does not move Redis to the extension system (that is t055).
- Does not implement dynamic (dlopen) loading.
- Does not write per-protocol documentation beyond the toy example.

## Accepted decisions

**Static linking over dynamic loading for Gate C.**
Why: benchmarking tool; deployment simplicity; no hot-path overhead.
Future: a follow-up ADR may add dlopen for third-party extension distribution if
there is a concrete need. Dynamic loading must not require changing `wrkx_extension.h`.
